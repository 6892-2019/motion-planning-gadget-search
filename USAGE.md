# Python Gadget Library — Usage Guide

The Python layer (`src/gadget*.py`) is an interactive toolkit for defining,
visualising, and reasoning about motion-planning gadgets: testing whether two
gadgets are the **same**, soundly **refuting** simulations, and **building and
verifying** explicit simulation constructions with step-by-step traces and
paper-style diagrams.

It sits alongside the exhaustive C++ search described in the [README](README.md);
use it to hand-check, prototype, or illustrate specific gadgets rather than run a
full exhaustive search.

For a gallery of worked examples (with diagrams), see
[`demo_output/REPORT.md`](demo_output/REPORT.md), generated by
`src/demo_simulations.py`.

---

## Quick start

```bash
# run from the repo root
python3 src/demo_simulations.py      # regenerates demo_output/ (incl. REPORT.md)
python3 -m unittest discover -s src -p 'test_*.py'   # run all tests
cd src && jupyter notebook gadget_exploration.ipynb  # interactive guide
```

> lacks these, run the demo with a Python that has `graphviz` installed (e.g. the
> system `python3`). SVGs are always written even when no PNG converter exists.

## Concepts

A **gadget** has:

- **states** — internal memory (integers `0 … n-1`).
- **locations** — ports the agent can enter/exit (integers `0 … m-1`).
- **transitions** — tuples `(from_state, from_loc, to_state, to_loc)`: "the agent
  enters `from_loc` while the gadget is in `from_state`, exits at `to_loc`, and
  the gadget moves to `to_state`". Entry and exit must differ (`from_loc ≠ to_loc`).

A **traversal mode** is one such tuple. A gadget may be **deterministic** or not,
**reversible** (every traversal can be immediately undone — the transition
relation is symmetric under `(s,a,s',b) ↦ (s',b,s,a)`), and/or a **DAG** (its
state-transition graph is acyclic, so it can be traversed only a bounded number
of times).

### Equivalence vs. simulation — keep them separate

- **Equivalence** asks: are two gadgets *the same gadget* — do they admit exactly
  the same traversal sequences? This is decided exactly by
  `behaviorally_equivalent` (determinise → minimise → canonicalise, then compare).

- **Simulation** asks: can a *system* of one gadget reproduce another? This is the
  notion used for hardness reductions (Ani–Demaine–Hendrickson–Lynch, *Trains,
  Games, and Complexity*, arXiv:2005.03192). It is **much stronger** than "B has
  all of A's traversal modes": a one-player simulation must match A's traversal
  sequences with an *if and only if*, so **extra** reachable behaviour *breaks* a
  simulation rather than helping it.

  > A toggle does **not** simulate a dicrumbler, even though it has the
  > dicrumbler's one transition: a system of reversible gadgets is itself
  > reversible and can never reproduce the dicrumbler's irreversibility. The
  > earlier `check_simulation` (single-step mode-subset) gave this false positive
  > and has been removed. See `demo_output/REPORT.md` §4.

We *refute* simulations soundly with `refute_simulation` (composition invariants),
and *confirm* them by building an explicit construction with `GadgetSystem` and
checking the gadget it induces.

The **closure** of a gadget adds shortcut transitions for chains that re-enter the
*same* port (cross-port chaining would be unsound). It is a derived reachability
view, used by `get_traversal_modes(take_closure=True)`.

## Translating YAML gadgets to Python

`src/toggles/*.yaml` define gadgets for the C++ search, format
`[from_state, from_loc, to_state, to_loc]`:

- `uedges` — undirected: the listed transition **and** its reverse are added.
- `dedges` — directed: only the listed transition is added.

```python
# YAML: toggle  uedges: [[0,0,1,1]]
toggle = Gadget(2, 2)
toggle.add_transition(0, 0, 1, 1)        # listed direction …
toggle.add_transition(1, 1, 0, 0)        # … and its reverse

# YAML: dicrumbler  dedges: [[0,0,1,1]]
dicrumbler = Gadget(2, 2)
dicrumbler.add_transition(0, 0, 1, 1)    # listed direction only
```

YAML gadgets with same-location transitions (`from_loc == to_loc`) are not
representable by the Python `Gadget` class and must be skipped/reinterpreted.

## Module reference

### `gadget.py` — the Gadget class

```python
g = Gadget(num_states, num_locations, reversible=False)
```

| Method | Returns | Notes |
|---|---|---|
| `add_transition(fs, fl, ts, tl)` | `bool` | `False` if out-of-bounds or `fl == tl`. With `reversible=True`, also adds the reverse. |
| `get_transitions_from(state, loc)` | `list[(to_state, to_loc)]` | All exits from an entry. |
| `closure()` | `Gadget` | New gadget with same-port shortcut transitions added (idempotent). |
| `trace(init_state, moves, …)` | `bool` | Steps a `(entry,exit)` sequence through one gadget, printing each step. |
| `is_equivalent_to` / `is_isomorphic_to` | `bool` | Structural transition-set isomorphism (state-only / state+location). For behavioural equality prefer `behaviorally_equivalent` below. |

### `gadget_simulation.py` — equivalence & simulation reasoning

```python
from gadget_simulation import (
    get_traversal_modes, print_traversal_table,
    is_reversible, is_dag, minimize,
    behaviorally_equivalent, refute_simulation,
)
```

- `get_traversal_modes(g, take_closure=True)` → `set` of mode tuples.
- `print_traversal_table(g, take_closure=False, state_labels, loc_labels, title)`
  — human-readable mode table, the easiest hand-check.
- `is_reversible(g)`, `is_dag(g)` — composition invariants (inspect the
  transitions, not the construction flag).
- `minimize(g)` → `Gadget` — DFA state-minimisation (deterministic gadgets).
- **`behaviorally_equivalent(A, B, fixed_locations=False)`** → `bool` — the
  authoritative equality test. Reduces each state's language to a canonical form
  (determinise → minimise → canonicalise) and compares the sets under relabeling;
  handles nondeterminism and redundant states. `fixed_locations=True` holds port
  indices fixed.
- **`refute_simulation(target, block)`** → `list[str]` — *sound* reasons no system
  of `block` can simulate `target` (reversibility; DAG/boundedness). A non-empty
  list is a proof of impossibility; an empty list means "not refuted" — **not** a
  proof that a simulation exists.

```python
behaviorally_equivalent(toggle, dicrumbler)          # False
refute_simulation(dicrumbler, toggle)                # ['reversibility: …']
```

### `gadget_system.py` — building & verifying constructions

A `GadgetSystem` is gadget **instances** wired together at their ports, with some
ports **exposed** as the external interface.

```python
from gadget_system import GadgetSystem

s = GadgetSystem()
s.add_instance('T1', toggle, initial_state=0).add_instance('T2', toggle, 0)
s.connect(('T1', 1), ('T2', 0))                      # wire two ports (a corridor)
s.expose('L', ('T1', 0)).expose('R', ('T2', 1))      # external interface ports
```

| Method | Returns | Notes |
|---|---|---|
| `induced_gadget()` | `(Gadget, configs, labels, defects)` | The gadget the system implements (states = reachable configurations). `defects` lists same-port traversals that change state — unfaithful behaviour. |
| `verify_simulates(target, label_to_target_loc=None)` | `bool` | `True` iff the induced gadget is `behaviorally_equivalent` to `target` and there are no defects. A pass is a genuine one-player simulation. |
| `trace(config, entry, exit, end_config=None)` | move list / `None` | One concrete agent path for a traversal. |
| `print_all_traces()` | — | One trace per allowed traversal, grouped by configuration. |

Moves in a trace are `('traverse', inst, from_loc, to_loc, from_state, to_state)`
or `('wire', from_port, to_port)`.

### `gadget_viz.py` — diagrams

```python
from gadget_viz import (
    visualize_state_diagram,           # states + labelled transition edges
    visualize_state_location_diagram,  # the (state, location) configuration graph
    visualize_gadget_box,              # paper-style: ports on perimeter, transitions inside
    visualize_system,                  # network of gadgets: boxes, wires, external tags
)
```

- `visualize_gadget_box(g, path, state_labels, loc_labels, title, port_sides)` and
  `visualize_system(system, path, positions, port_sides, highlight_entry,
  highlight_moves, state_labels, title)` produce **paper-style** diagrams (rounded
  boxes, ports on the perimeter in cyclic order, transitions inside as arrows with
  one style per state, wires between connected ports, green external tags). They
  write `<path>.svg` and (if a converter exists) `<path>.png`.
  - `port_sides` pins ports to edges, e.g. `{0:'L', 1:'R', 2:'L', 3:'R'}` to lay
    tunnels out horizontally; for a system it is keyed by instance name.
  - `positions={name:(col,row)}` lays instances out (a column suits parallel bundles).
  - `highlight_moves` (a list from `GadgetSystem.trace`) overlays the agent's path
    in red with numbered steps.
- Legacy/abstract styles: `visualize_gadget_automaton`, `visualize_gadget_circular`,
  `visualize_gadget`, `visualize_gadget_comparison` (Graphviz, PNG).

### `gadget_notebook.py` — inline Jupyter helpers

`show`, `show_table`, `show_automaton`, `show_comparison` — display diagrams/tables
inline without leaving temp files.

## Typical workflows

**Are these two gadgets the same?**

```python
print_traversal_table(A); print_traversal_table(B)
behaviorally_equivalent(A, B)            # exact answer
```

**Can a system of B simulate A?**

```python
refute_simulation(A, B)                  # sound impossibility check first
# if not refuted, build a candidate construction and verify it:
s = GadgetSystem(); s.add_instance('b1', B, 0); ...; s.expose(...)
s.verify_simulates(A, label_to_target_loc={...})
s.print_all_traces()                     # inspect the agent's paths
visualize_system(s, 'out/construction', highlight_entry='L',
                 highlight_moves=s.trace(s.initial_config(), 'L', 'R'))
```
